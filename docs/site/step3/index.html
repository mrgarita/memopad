「メモ帳に比べ、キータッチしたときに一呼吸置いてからエディタ部分に表示される。キー入力に表示が追い付いていない。シンプルなメモ帳でこのレスポンスの悪さは致命的」というフィードバック。IME（日本語入力）のときに特に気になるとのこと。

2.2 調べ方

体感を数値にするため、2 段階で計測した。

  1. アプリ内部の処理時間。環境変数 MEMOPAD_PERF=1 で有効になる診断ログ（Services/PerfLog.cs）を組み込み、キー押下（KeyDown）→本文変更（TextChanged）→描画（CompositionTarget.Rendering）の各時刻と、ウィンドウ メッセージ・Dispatcher の処理時間を %TEMP%\memopad-perf.log に記録した。
  2. 入力から画面に出るまでの時間。PowerShell から keybd_event でキーを 1 つ送り、画面上部をキャプチャし続けてピクセルが変わるまでの時間を測るスクリプトを書いた。IME は 半角/全角 キーを送って ON にし、「nihongo…」とローマ字を 1 文字ずつ送る。同じ手順をメモ帳にも当てて比べる。キャプチャ 1 回に約 18 ms かかるので、精度はその程度。

2.3 結果

アプリ内部は速かった。キー押下から本文変更まで 3〜5 ms、描画要求まで +2 ms で、115 KB のファイルでも変わらない。ステータスバー更新などの自前処理は 0.01 ms。つまり アプリのコードが遅いのではなかった。

一方、画面に出るまでの時間はメモ帳の 2.5 倍あった。WPF の TextBox は、UI スレッドが描画内容を作ってから別の描画スレッドが DirectX で描き、それを DWM（デスクトップ合成）が画面に出す、という 3 段階を経る。その途中で垂直同期に合わせて待つため、1〜2 フレーム（16〜33 ms）分の遅れが構造的に乗る。テーマ（Fluent）を外しても、ソフトウェア描画に切り替えても変わらなかった。

8.5 WPF の下限と Windows Forms との比較

どこまで縮められるかを知るため、最小構成のアプリを同じ条件（self-contained 発行、同じ端末）で測った。

  • WPF は空に近いウィンドウでも約 400 ms かかる。ランタイム起動 60 ms ＋ WPF Application 初期化 80 ms ＋ XAML／テンプレート／HWND 生成／Direct3D／初回描画で、memopad の機能を削っても 400 ms を下回れない。メモ帳の 200 ms は WPF の構造上届かない。
  • Windows Forms なら約 160 ms で、メモ帳より速い。本文の RichEdit はすでに Windows Forms のコントロールなので、メイン ウィンドウ（タイトル行のタブ、メニュー、検索バー、ステータスバー）を Windows Forms で作り直せば、起動はメモ帳並みになる見込み。ダイアログ類は WPF のまま残しても、開くときに初めて WPF を初期化すればよい。

10. FB-13：タイトル行でウィンドウを動かせない（v0.9.0）

10.1 現象

10.2 原因：当たり判定を子コントロールが横取りしていた

MemoPad は標準のタイトル バーを WM_NCCALCSIZE で外し、「ここはタイトル行（HTCAPTION）」「ここは左の縁（HTLEFT）」といった判定を MainForm が WM_NCHITTEST で答えている。ところが Windows は、その座標にある いちばん手前の子ウィンドウ に当たり判定を尋ねる。v0.7.0 までの WPF はウィンドウ全体が 1 つの HWND だったので親がそのまま答えられたが、Windows Forms はコントロールごとに HWND があるため、タイトル行を覆う TitleBar、四辺を覆う RichEdit やステータスバーが「ここは普通のクライアント領域（HTCLIENT）」と答えてしまい、親の答えは使われない。

どのウィンドウにマウス入力が届くかは WindowFromPoint で調べられる。v0.8.0 では、フォーム自身は正しく答えているのに、入力先はすべて子コントロールだった。

12. FB-16：ドラッグ＆ドロップで開くと編集済みになる（v0.9.1）

12.1 現象

エクスプローラーから既存のテキスト ファイルを本文の上にドラッグ＆ドロップして開くと、開いた直後なのに タイトルに *、タブに●が付いて「編集済み」の状態になる。本文の内容と文字数は正しく、そのまま閉じようとすると 保存の確認ダイアログが出てしまう。メニューの「開く」やエクスプローラーからの「プログラムから開く」では起きない。

12.2 原因：ドロップを RichEdit にも処理させていた

本文の RichEdit は OLE のドロップ先を自分で登録していて、Windows Forms はそこに相乗りする形で DragDrop イベントを出す。MemoPad はそのイベントでファイルを開いていたが、イベントを出したあとに RichEdit 自身のドロップ処理が続く。プレーン テキスト モードでは実際には何も貼り付けられないものの、 変更通知（EN_CHANGE）だけが上がるため、直前に読み込んだばかりの文書が「編集済み」と判定されていた。

ドロップ先のタブが空の「タイトルなし」だと、そのタブを使い回してファイルを読み込む（メモ帳と同じ挙動）ので、 読み込んだ文書そのものに●が付く。本文に何か書いてある状態で落としたときは別のタブが作られるため、 新しいタブは●にならず、現象が見えにくかった。

12.3 直し方：ドロップ先を自前のものに差し替える

Views/FileDropTarget.cs に IDropTarget の実装を追加し、RichEdit のハンドルができたところで RevokeDragDrop→RegisterDragDrop と差し替える。受け付けるのはファイル（CF_HDROP）だけで、 ドロップされたデータは RichEdit に渡さない。これで「ファイルを開くだけ」の動作になる。 ファイルを開く処理自体は BeginInvoke で後回しにして、ドロップの処理中にドラッグ元を待たせないようにした。

13. FB-17：ホイールで最後の行まで届かない（v0.9.2）

13.1 現象

「長いファイルをマウス ホイールでスクロールしたとき、最後の改行までスクロールされなかった。メモ帳では問題なく最後の改行まで届く。些細なことだが気になる」というフィードバック（再現用のファイルも受け取った）。 ファイルの末尾が改行で終わっていると、その改行のあとに空の行が 1 行あり、カーソルもそこへ置ける。メモ帳はホイールでこの空行が見える位置まで送れるが、 MemoPad は最後の文字の行が画面の下端に来たところで止まり、それ以上回しても動かなかった。

14. FB-18：折り返しなしで横にスクロールできない（v0.9.2）

14.1 現象

14.2 原因：Windows Forms の WordWrap が true のままだった

Windows Forms の RichTextBox は、自分の WordWrap プロパティが true（既定）だと、ウィンドウを作るときに 横スクロールバー（WS_HSCROLL）と、カーソルに合わせて横に送る指定（ES_AUTOHSCROLL）を付けない。 MemoPad は折り返しを切り替えても元に戻す履歴が消えないよう、WordWrap を使わず RichEdit に直接 EM_SETTARGETDEVICE を送って切り替えている （WordWrap を変えるとウィンドウが作り直され、履歴が消える）。そのため WordWrap は既定の true のまま残り、 折り返しを外しても横に送る手段がなかった。本文のウィンドウのスタイルを調べると、実際に 2 つとも付いていなかった。

14.3 直し方

  • PlainTextEdit のコンストラクター（ウィンドウを作る前）で WordWrap = false にして、2 つのスタイルが付くようにした。折り返しの切り替えはこれまでどおり EM_SETTARGETDEVICE で行うので、元に戻す履歴は残る。
  • ところが RichEdit は、「折り返しなし→あり」に切り替えても横スクロールバーを自分では片付けず、表示の高さの計算がスクロールバー 1 本分（26 px）ずれたままになった。折り返しを切り替えるときに EM_SHOWSCROLLBAR で横スクロールバーを明示的に隠す（折り返さないときは使える状態に戻す）ようにした。折り返さないときも、長い行が無ければ RichEdit が自動で隠す。

  • プロセスの CPU 時間 ＝ 読み込みが終わったあとも計算が続いているか
  • 本文の縦スクロール範囲 ＝ 折り返しの計算が進んでいるか

条件忙しい区間その間の CPUその間の往復時間収まったあと

なぜカクつくのか

Scintilla は折り返し位置の計算を一度にやらず、10 ms ずつに区切って空き時間に進める（Windows 版では 10 ms 間隔のタイマーで 1 回分を回す。タイマーのメッセージは順番待ちの列が空のときだけ届く低優先度のもの）。 計測した往復時間の中央値 9.7 ms・90 % 点 10.0 ms は、この 1 回分の長さがそのまま出たもの。

ウィンドウをドラッグしている間、Windows はアプリと同じスレッドの中で移動用のループを回している。 マウスの移動と折り返しの計算が同じ列に交互に並ぶので、1 コマ描くたびに最大 10 ms 余分に待つ。 画面の 1 コマは 16.7 ms（60 Hz）なので、半分以上を計算に持っていかれる計算になり、動きが飛んで見える。 全行の計算が終わるとタイマーは止まり、往復は 0.1 ms に戻る――ユーザーの言う「3 秒ほど待つとスムーズ」はこれ。

これは FB-19 で RichEdit から Scintilla に替えたときの仕組みそのものでもある。 同じ量の計算を、RichEdit は一度にやって 43 秒固まり、Scintilla は 10 ms ずつに割るので固まらない。 ただし割って進めている間は、他の操作と CPU を分け合うことになる。トレードオフの表と裏の関係にある。

今回のファイルは 1 行 41 文字で、このウィンドウ幅では実際には 1 行も折り返さない（縦スクロールの範囲は 120,000 行のまま変わらない）。 それでも「折り返す必要がない」と判断するには 120,000 行すべての幅を測る必要があるので、同じ約 4 秒がかかる。 折り返しオフでこの区間がまったく無いのは、Scintilla が画面に出ている行の幅しか測らないため。

17. FB-22：端末を起動して最初の起動だけ遅い（v0.10.2）

17.1 見立て

2 回目以降が速いのは、1 回目に読んだ DLL が Windows のファイル キャッシュ（メモリ）に残るため。端末を起動した直後はキャッシュが空なので、 DLL をディスクから読み、Defender の初回の検査も受ける。MemoPad は .NET ランタイムを同梱しているので、使う DLL はすべて MemoPad のフォルダーにあり、ほかのアプリと共有されない（メモ帳の部品は Windows 自身がすでに読み込んでいる）。 つまり起動時に触るファイルの量が、そのまま初回の時間になる。

余白は Scintilla の 0 番の欄（マージン）で作っている。欄の種類が「記号（Symbol）」だと行番号用のスタイルの背景色で塗られ、 その色は全スタイルをそろえる StyleClearAll の中で、わざわざシステムの灰色（COLOR_3DFACE）に戻される。 白い背景では #F0F0F0 と白の差がほとんど目立たないので、v0.10.0 から気づかなかった。欄の種類を 「本文の背景色（MarginType.BackColor）」に変えて直した。

18.2 太さ：メモ帳も 1 px

「太さを変えればよいか」という相談について：太さはメモ帳も MemoPad も 1 px で同じだった（Windows の「テキスト カーソルの太さ」が既定の 1 のとき）。 見づらさの主因は 18.1 の帯なので、太さは変えずに、Windows の設定（アクセシビリティ → テキスト カーソル → テキスト カーソルの太さ）に従うようにした。 Scintilla はこの設定を読まないので、v0.10.1 までは設定で太くしても MemoPad だけ 1 px のままだった。起動時に設定を読み、 設定が変わったときの通知（WM_SETTINGCHANGE）でも読み直す。起動中に 1 → 4 → 1 と変えて、キャレットが 1 → 4 → 1 px に追従することを確かめた （Scintilla.NET 7.0.0 は幅を 3 px までに制限していたが、7.1.1 で Scintilla 本来の 20 px まで使える）。

19. FB-24：メニューのアクセス キーが効かない（v0.10.2）

19.1 見つけた経緯と現象

FB-22 の確認で撮影スクリプト（capture-memopad.ps1）を流すと、フォント・色変更などのダイアログが 1 つも開かなかった。 修正前の v0.10.1 でも同じだった。キー入力を再現して調べると、Alt+O で書式メニューは開くが、続けて F を押すと メニューが閉じて本文に「f」が入る（IME がオンなら未確定の文字になる）。矢印キーと Enter では選べる。 フォーカスが検索バーの入力欄にあるときは正しく開いた。IME は Meltype と Microsoft IME のどちらでも同じだった。

19.2 原因：IME の確定文字はメニューを素通りする

Windows Forms のメニューは、開いている間もフォーカスを本文に残したまま、キー入力のメッセージ（WM_KEYDOWN・WM_CHAR）を メッセージ ループの段階でメニューへ付け替えて、アクセス キーを受け取っている。本文（Scintilla）に届いたメッセージを記録すると、 F を押したときに届いていたのは WM_KEYDOWN ではなく、IME からの WM_IME_STARTCOMPOSITION → WM_IME_COMPOSITION（確定文字「f」）→ WM_IME_ENDCOMPOSITION だった。IME の確定文字はフォーカスのあるウィンドウへ直接送られるので、 付け替えを通らない。Windows 標準のメニューはメニューの間 IME を止めるが、Windows Forms のメニューは止めない。

RichEdit 時代（v0.9.x）の撮影スクリプトではダイアログを撮れていたので、本文を Scintilla にした v0.10.0 から起きていたとみられる。

19.3 直し方

メニューが開いている間（メニュー バーは MenuActivate〜MenuDeactivate、右クリック メニューなどは Opened〜Closed）だけ、フォーカスのある部品から IME を切り離し（ImmAssociateContext に NULL）、 閉じたら元に戻す（MainForm.Menu.cs の SuspendImeForMenu／ResumeImeAfterMenu）。Windows 標準のメニューと同じ振る舞いになる。

25. FB-30：Ctrl+Z で取り消す単位がおかしい（v0.10.5）

「既存のファイルでは 1 文字ずつ取り消されるのに、新規のファイルでは入力したものが全部消える」との報告。既存のファイルでは日本語を入力していた。 v0.10.4 で、入力のしかたを変えながら「入力 → Ctrl+Z を 1 回ずつ押す → そのたびに本文を取り出す」を自動で繰り返して調べた（本文は UI Automation から読めないので、Ctrl+A → Ctrl+C で取り出した）。

新規と既存で違いは出ず、どの入力でも「続けて入力した分が 1 回の Ctrl+Z で全部消える」だった。報告の「1 文字ずつ」は再現できなかった。 1 文字ずつになるのは、Insert キーで上書きモードにしたとき（Scintilla が 1 文字ごとに区切る。上書きモードはタブごとに切り替わる）だけ見つかった。 いずれにしても、メモ帳とは単位が違う。メモ帳で同じように試すと、「単語とその後ろの空白」ごとに取り消され（空白の次に文字を打つと新しい単位になり、「.」では区切らない）、日本語は確定ごとだった。 ユーザーと相談し、取り消す単位をメモ帳と同じにすることにした。単位が決まっていれば、入力のしかたによらず同じ動きになる。

25.2 原因：Scintilla は続けて打った文字を 1 つにまとめる

Scintilla は、編集を 1 回ずつ「元に戻す履歴」に積むとき、直前の操作と同じ種類（挿入なら挿入）で位置が続いていれば、前の操作と 1 つの単位にまとめる。 単語の切れ目でも IME の確定でも区切らないので、カーソルを動かさずに打ち続けた分はすべて 1 つになっていた。区切られるのは、カーソルを動かして別の場所に打ったとき、削除をはさんだとき、貼り付けなどの別の操作をしたときだけ。

25.3 対策：文字が入る前に、メモ帳の切れ目で区切る

Scintilla には「ここから先は前の操作とまとめない」と直接指示する API は無いが、空の BeginUndoAction／EndUndoAction を 1 組呼ぶと、直前の操作に「まとめない」印が付く。 PlainTextEdit の WndProc で、文字が本文に入る前のメッセージ（WM_CHAR、Enter・Tab の WM_KEYDOWN、IME の確定 WM_IME_COMPOSITION）を受け、次のときにこの印を付ける。

  • 空白以外の文字を打つとき、カーソルの直前が空白・タブ・改行なら（単語の始まり）
  • 日本語などを含む IME の確定の前と、その次の入力の前（確定ごとに 1 つの単位）。確定した文字列は ImmGetCompositionString で読むだけで、Scintilla の処理には触らない
  • 半角英数だけの確定は、キーで打った文字と同じ扱いにする（1 文字ずつ確定を送る IME でも、単語ごとにまとまるように）

選択範囲を置き換える入力と上書きモードは、Scintilla が自分で区切るので何もしない。貼り付け・切り取り・削除の単位も今までどおり。

27. つまずいた点のメモ

  • 体感の遅さは、まず数値にする。アプリ内部のログだけ見ると「速い」と結論しかねなかった。画面のピクセルが変わるまでを別プロセスから測って初めて、メモ帳との差（19 ms 対 50 ms）が見えた。
  • PowerShell 5.1 は $null を文字列引数に渡すと空文字になる。FindWindow($null, "title") がクラス名 "" で検索して失敗した。[NullString]::Value を渡す。
  • PowerShell の -WindowStyle Hidden は子の Windows Forms フォームまで隠す。計測用のホスト ウィンドウが出ず、しばらく原因が分からなかった。
  • スクリプト ファイルは BOM 付き UTF-8 で保存する。BOM 無しだと PowerShell 5.1 が ANSI として読み、日本語のコメントで構文が壊れる。
  • ビルドが 1 回おきに失敗する原因はビルド サーバーだった。前回の MSBuild ノードや VBCSCompiler が obj の生成ファイルを掴んだままになる。dotnet build-server shutdown してから -nodeReuse:false -p:UseSharedCompilation=false でビルドすると安定した。
  • Fluent の MenuItem は高さを縛ると消える。Menu に Height=30 を付けただけで項目が描画されなくなった。テンプレートを差し替えるのが確実。
  • 撮影スクリプトはプログラムからの操作が多く、マウス操作の不具合を見逃す。タブの切り替えは UI Automation の Invoke や SelectedItem の設定では動いてしまう。ユーザーが実際に行う操作（マウス クリック）そのものを再現する確認を、機能ごとに 1 つは持つ。
  • 表示スケールを決め打ちしない。この端末は 150 % で、125 % と思い込んで換算した値が合わなかった。GetDpiForSystem で確かめてから換算する。
  • 起動時間は「どこか 1 か所」ではなく積み上げで決まる。段階ごとの経過時間を記録して初めて、WPF の固定費が全体の 8 割を占めると分かった。最小構成のアプリで下限を測るのが早道だった。
  • 複合 ReadyToRun は初回起動を測ってから採用を決める。温まった状態の数字だけ見ると速いが、新規コピー（インストール直後相当）の初回起動は 3 秒以上悪化した。
  • dotnet-trace は対象を強制終了するとトレースが途中で切れる。JIT イベントの集計はできたが、CPU サンプリングはスタックが解決できず使えなかった。対象が自分で終了する形にする。
  • 速くするより先に、どこまで速くできるかの下限を測る。最小構成の WPF（約 400 ms）と Windows Forms（約 160 ms）を作って比べたことで、「WPF のままでは無理」と早く結論でき、作り直しの判断材料になった。
  • 自前のタイトル バーは、子コントロールが当たり判定を横取りする。親フォームが WM_NCHITTEST で HTCAPTION と答えても、その座標に子ウィンドウがあると Windows は子に尋ねる。1 枚の HWND で描く WPF から、コントロールごとに HWND を持つ Windows Forms に移ると必ず踏む。子から HTTRANSPARENT を返して親へ譲る。
  • ウィンドウの移動・リサイズは実際のマウス操作で確かめる。WindowFromPoint は HTTRANSPARENT を無視して子ウィンドウを返すので、これだけでは直ったか分からない。mouse_event でドラッグして、ウィンドウの位置とサイズの変化を見るのが確実。
  • ToolStripMenuItem の Padding は左右が効かない。メニュー項目の字下げを変えようと 4 → 13 → 40 px と変えても文字の位置は 1 px も動かなかった（効くのは上下＝項目の高さだけ）。左右はポップアップ側のアイコン欄（ShowImageMargin）と内部レイアウトが決めている。値を変えて撮影・実測する確認を挟まないと、効かない設定をそれらしいコメント付きで残してしまう。
  • RichEdit はドロップを自分でも処理する。Windows Forms の DragDrop イベントでファイルを開いても、そのあとに RichEdit 側の処理が走って変更通知が上がる。貼り付けられる中身が無くても通知だけは来るので、開いたばかりの文書が「編集済み」になった。ドロップ先（IDropTarget）ごと自前のものに差し替えるのが確実。
  • ドラッグ＆ドロップの不具合は本物のドラッグでないと再現しない。自前のウィンドウから DoDragDrop で送ったドロップは RichEdit に拒否されて素通りした。エクスプローラーが渡すデータ オブジェクトには複数の形式が入っていて、挙動がまったく違う。エクスプローラーの項目の位置を UI Automation で取り、実際のマウス操作でドラッグするのが確実。
  • 「メモ帳の RichEdit」と「Windows の RichEdit」は別物。メモ帳はアプリに同梱した Office 系の riched20.dll（16.0）を使っていて、MemoPad が使う Windows 標準の msftedit.dll とは版が違う。メモ帳で起きないからといって同じ部品で起きないとは限らない。プロセスが読み込んでいるモジュールの一覧で確かめる。
  • ポインターを渡すメッセージは別プロセスから送れない。EM_SETSCROLLPOS を PowerShell から送ると、ポインターが相手のプロセスでは無効で、MemoPad 側で値が壊れた（計測側の誤り）。Windows が中身を運んでくれるのは一部の標準メッセージだけ。小さな検証用アプリの中で試すのが確実。
  • 計測がアプリを遅くすることがある。読み込みの完了を知ろうと 1 ms ごとに WM_GETTEXTLENGTH を送ったら、UI スレッドが応答に追われ、読み込みが数十秒かかるように見えた。読み込み中はメッセージを送らず、画面の変化と WM_NULL の往復時間で見る。GetPixel を点ごとに呼ぶのも DWM 越しでは非常に遅いので、範囲をまとめて写し取って比べる。
  • PowerShell の関数名は既存のエイリアスに負ける。SI（Set-Item）や Sc（Set-Content）という名前の関数を作っても、呼ぶとエイリアスのほうが動く。検証スクリプトの関数名は長めに付ける。
  • Windows Forms の RichTextBox.WordWrap はスクロールバーのスタイルまで決める。true のままだと横スクロールバーも横送りも付かない。折り返しを RichEdit へ直接指示して切り替える作りでは、見落としやすい。
  • 自前描画はアクセシビリティを落とす。1 枚のコントロールに描いたタブは、見た目は同じでも支援技術からは何も見えない。実体のあるコントロール（Button 継承）にすると標準の仕組みに乗る。
  • アセンブリ属性 1 つで 23 MB 読み込まれる。WPF テンプレートの ThemeInfo や、パッケージの Content に WPF のビルドが付ける属性は、どこからも使っていなくても、Windows Forms が exe の属性を調べるだけで WPF 本体を引き込む。「使っていない DLL がなぜ読まれるか」は AppDomain.AssemblyLoad で呼び出し元のスタックを残すと一発で分かる。
  • 初回起動の問題は、温まった状態の計測では見えない。robocopy /J（バッファーを使わないコピー）で新しい場所へ写すと、管理者権限も再起動も無しに「キャッシュに無い状態」を作れる。普通のコピー＋全ファイル読み込みと組み合わせると、ディスクと Defender の取り分も分けられる。
  • 配色の不具合は、利用者の配色で確かめる。左の余白の灰色は白い背景では見えず、v0.10.0 から誰も気づかなかった。撮影スクリプトは設定を退避して既定の配色で撮るので、濃い配色での見え方は別に確かめる。
  • IME の確定文字はメッセージ ループの付け替えを通らない。Windows Forms のメニューは本文にフォーカスを残したままキー入力を横取りする作りなので、IME が有効な部品にフォーカスがあるとアクセス キーが効かない。日本語環境では「IME がオンのまま」が普通の状態なので、キー操作の確認は IME オンでも行う。
  • 保存しない SystemParametersInfo の変更では WM_SETTINGCHANGE が配られない。テキスト カーソルの太さを一時的に変えて追従を確かめようとして、通知が届かず悩んだ。利用者の設定を書き換えずに試すには、値だけ変えて通知は対象に直接送る。
  • 画面の大きさは「解像度 ÷ 表示スケール − タスク バー」で考える。1920×1080 でも 150 % なら、ウィンドウを置ける高さは論理 672 px しかない。開発機の画面に収まっていても安心できない。ダイアログは作業領域の高さを上限にし、はみ出す分は一覧などの一部だけをスクロールさせて、ボタンは常に見えるようにする。
  • WPF の AccessText を中身にしたボタンは、名前が空になる。見た目では分からず、読み上げソフトや UI Automation でしか気づけない。アクセス キーのために AccessText を使うときは AutomationProperties.Name も付ける。撮影スクリプトが要素を名前で探していたおかげで見つかった。
  • 拡張子のないファイルは「.」という名前のキーで扱われる。Software\Classes\.\OpenWithList に入れると、Makefile や LICENSE の「プログラムから開く」にも出る。レジストリの API は「.」を特別扱いしないので、普通のキーとして作れる。
  • 「プログラムから開く」の候補は、画面を開かずに API で確かめられる。SHAssocEnumHandlers（拡張子単位）や BHID_EnumAssocHandlers（ファイル単位）は、Explorer の右クリックと同じ一覧を返す。OpenAs_RunDLL で画面を出す方法は、スクリプトから起動するとすぐ閉じて使えなかった。
  • ただし「候補に並ぶ」と「メニューに出る」は別。.bat は API では MemoPad が候補に並んでいたが、Windows が右クリックに「プログラムから開く」自体を出さなかった（FB-31）。最後は実際の右クリックで確かめる。
  • Scintilla の「元に戻す」は、続けて打った文字を 1 つにまとめる。区切る専用の API は無いが、空の BeginUndoAction／EndUndoAction を 1 組呼ぶと、直前の操作に「まとめない」印が付く。文字が入る前（WM_CHAR や IME の確定を受けた時点）に呼ぶ。
  • IME で変換中に押した Ctrl+Z は、本文ではなく IME に届く。Meltype では 1 回目で確定だけが起きた。元に戻す動きを確かめるときは、確定してから押す場合と分けて試す。
  • Windows 11 の右クリックの最初の階層は、パッケージの項目だけ。レジストリの shell に書いた項目は「その他のオプションを確認」の中に入る。VS Code も最初の階層に出すために、署名付きのスパース パッケージを別に登録している。
  • .NET の製品バージョンには、既定でコミット番号が付く。.NET 8 以降の SDK は、Git のリポジトリでビルドすると InformationalVersion に +<コミット番号> を足す。ファイルのプロパティの「製品バージョン」が 0.10.5+c80201d… になり、署名の条件「製品バージョンをそろえる」に合わなかった。IncludeSourceRevisionInInformationalVersion を false にして外す。
  • PowerShell はレジストリのパスの * もワイルドカードとして扱う。Test-Path 'HKCU:\Software\Classes\*\shell' は、すべての種類の shell キーに一致してしまう。* というキーそのものを調べるときは -LiteralPath を使う。
